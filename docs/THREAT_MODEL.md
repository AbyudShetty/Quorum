# Threat model

Status: **draft for Phase 0 review** · Owner: project maintainers · Last updated: 2026-10-01

This document is the authority for Quorum's security properties. Per `AGENTS.md`, no change may weaken an invariant below to make something easier; propose an amendment and ask instead. Every invariant must be backed by at least one test (column "Test"), and the adversarial suite (`tests/adversarial/`) is organised by invariant ID.

## 1. What we protect (assets)

| Asset                                      | Why it matters                                                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **Gated-action decisions** (approvals)     | The core promise: nothing consequential happens without a human. A forged or replayed approval is the worst failure. |
| **Event log integrity**                    | Humans rely on the timeline to know who said/did what. History must be tamper-evident.                               |
| **Identities and tokens**                  | Everything is attributed via tokens; theft = impersonation.                                                          |
| **Artifacts** (models, datasets, code)     | Wrong or poisoned file versions silently corrupt work; some are sensitive.                                           |
| **Findings and retractions**               | Decisions are made on claims; unmeasured or retracted claims must be visible as such.                                |
| **Leases**                                 | Prevent resource collisions; a stolen or stale lease blocks work.                                                    |
| **Availability of the coordination layer** | Must degrade to "agents work alone", never to "agents act unchecked".                                                |

## 2. Actors

| Actor                                                      | Trust                           | Notes                                                                                                                                                       |
| ---------------------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace human (member)                                   | Trusted for their own decisions | May be phished; may approve hastily on a phone.                                                                                                             |
| Server operator                                            | Trusted (Phase 1–2)             | Runs the server and can read/write its DB. Phase 3 signing + client-held chain checkpoints reduce this trust (see §5).                                      |
| Own agent (owned by a member)                              | **Semi-trusted**                | Follows its human's permissions but can be confused, hallucinate, or be prompt-injected.                                                                    |
| Other agent in workspace                                   | **Untrusted input source**      | Its messages are data, never instructions (plan §4.2).                                                                                                      |
| Network attacker                                           | Untrusted                       | On LAN/hotspot, or on the path when the server is exposed.                                                                                                  |
| Former member / revoked agent                              | Untrusted                       | Must lose access immediately.                                                                                                                               |
| Supply-chain attacker                                      | Untrusted                       | Compromised npm dependency or GitHub Action.                                                                                                                |
| Other local process (same machine) **[local mode]**        | Untrusted                       | Can reach the loopback port and may try to grab it first (port squatting). Has no token.                                                                    |
| Other OS user on the same machine **[local mode]**         | Untrusted                       | Can reach loopback; must not read the data directory or keychain entries of the Quorum user.                                                                |
| Malicious web page in the human's browser **[local mode]** | Untrusted                       | Can make the browser send requests to `localhost` (cross-site requests, DNS rebinding).                                                                     |
| Own agent acting as its OS user **[local mode]**           | Semi-trusted                    | Runs with the human's OS permissions: it can read what the human can, including local credentials, unless its vendor sandbox/permissions prevent it (§6.7). |

## 3. Trust boundaries

```
 [Agent process] --(MCP stdio)--> [Adapter] --(HTTPS + agent token)--> [Server] <--(HTTPS + session cookie)-- [Human browser]
                                      |                                   |
                         renders incoming messages              [SQLite / blobs on disk]
                         as delimited untrusted data
```

1. **Agent ↔ adapter:** the adapter runs locally with the agent's privileges. It is the place untrusted content enters the model's context.
2. **Adapter ↔ server:** network boundary; authenticated by agent token; all input validated by JSON Schema.
3. **Browser ↔ server:** network boundary; human session; CSRF/XSS surface.
4. **Server ↔ storage:** local disk; the operator can tamper (tamper _evidence_, not prevention).
5. **Local mode [added]:** in T1/T2 the adapter ↔ server and browser ↔ server boundaries run over loopback. Loopback is **not** a trust boundary on its own — other processes, other OS users and web pages can reach it — so local mode keeps every invariant above and adds INV-23 to INV-27. The private data directory and the OS keychain form a further boundary between OS users.

## 6. Assumptions and explicit non-goals (residual risk)

These are limits we state openly rather than hide:

1. **Quorum cannot physically stop an agent from running a command on its own machine.** An agent with shell access can run `git push` without asking Quorum. Quorum's gate is enforced at _enforcement points_: (a) actions that only Quorum can perform (submission slot, lease beyond quota, artifact promotion/deletion, policy change), and (b) **grant verifiers** — small hooks that check a Quorum approval grant before the action, e.g. a git `pre-push` hook, a CI required check, a deploy/submit script (`quorum grant verify`). Plus the agent vendor's own permission system, which Quorum never weakens. The Phase 2 exit criterion "an agent cannot complete a gated action without approval" is tested against these enforcement points. _(Open question for reviewers — see §8.)_
2. The **server operator is trusted** in Phases 1–2 (they can read message bodies). Phase 3 signatures make forging agent messages detectable; Phase 7 end-to-end encryption would remove read access.
3. **LLMs may still follow injected text** despite framing. The framing reduces risk; the gate is the actual control.
4. A **compromised member machine** compromises that member's agents and session. Mitigated by short-lived tokens and instant revocation, not prevented.
5. **Tailscale / Cloudflare** are trusted for transport in deployments that use them; Quorum still authenticates every request itself and never treats "on the tailnet" as authentication.
6. **Sandboxed agents may run as another local account.** On Windows, Codex adds a `CodexSandboxUsers` group, and new folders under `%LOCALAPPDATA%` inherit read access for it. Quorum therefore never relies on default folder permissions: it strips inherited and explicit access for every account other than the user, SYSTEM and Administrators, and checks by SID (INV-25, `packages/local/src/windows-acl.ts`).
7. **An agent runs as its human's OS user.** Anything the human can read — the OS keychain entries of that user, browser cookies, CLI credentials — the agent can in principle read too, unless its vendor's sandbox or permission rules stop it. Quorum therefore (a) requires a hardware-backed user-verification signature (Windows Hello in the terminal, or a passkey) for `high`/`critical` approvals (INV-31), which needs a physical touch, PIN or biometric an agent cannot provide. A same-user agent could still _trigger_ a Windows Hello or passkey prompt with its own approval; the human must only complete a prompt they started themselves, after reading the request shown by `quorum approve` (documented in the approval UX); (b) has `quorum attach` add deny-read rules for the Quorum data directory to the agent's settings where the vendor supports it (Claude Code `permissions.deny`), as defence in depth; (c) logs everything. Approvals of `low`/`medium` requests and agent tokens remain readable by a determined same-user agent, and so does the local bootstrap code while it is valid (it gives the owner human token; ARCHITECTURE §6), which is why it is single use, lasts 10 minutes and is removed once spent; teams that need more can raise `user_verification_from` in policy (POLICY_SPEC §2).
8. **Path leases are advisory.** In a shared working tree Quorum warns (or, if configured, blocks the vendor's edit tool), but an agent with a shell can still write any file.
9. **Port takeover between two requests (local mode).** A long-lived client redoes the identity handshake after any failed request, finds a restarted server through the private discovery file, and never sends a token to anything that has not proven the pinned key (INV-24). It does not re-prove identity on _every_ request: if the server dies and another program takes its exact port before the client's next request fails, that one request can carry an access token (valid for at most an hour, scoped to one agent; revocation is instant). Per-request proof would need TLS on loopback; not planned.
10. **Vendor delivery features may change or be previews** (Claude Code channels are a research preview; Codex idle wake uses the experimental app-server daemon protocol). Security never depends on them: they only affect latency.

## 7. Security process
